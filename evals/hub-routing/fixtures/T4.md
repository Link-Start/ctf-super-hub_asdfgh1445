## 本轮判读

这是一道 Web 鉴权类 CTF：登录后的 cookie 是自定义加密 token，核心链条是「还原 token 算法 → 伪造 admin → 拿 flag」，外加一条队规级验收要求（赛后交可复现 writeup）。已进入 **模式 A：自动分流**。

## 为什么走这条

- 题目主战场是 Web 登录态与鉴权绕过，`ctf-web` 的 description 直接覆盖（JWT、鉴权绕过、session 伪造），产出物就是 flag——它是主 skill。
- token 是「自定义加密」而非现成协议，算法还原是形成伪造结论前的独立环节，`ctf-reverse` 按角色表承担「证据补充：算法还原」。
- 队规要求解完后交可复现题解，`ctf-writeup` 承担「验收约束：复现检查」，在主结果形成后介入。
- 三个要求彼此独立且会改变方向/验收，单 skill 覆盖不全，因此组队：**1 主（ctf-web）+ 2 辅（ctf-reverse、ctf-writeup）**，不超编。

## 下一步（按顺序）

1. 调用 `/ctf-web`（主）：从登录请求/响应入手，先解码 cookie、判断 token 形态，再定位服务端如何校验它。
2. 视证据形态调用 `/ctf-reverse`（辅）：若题目提供了实现该加密的二进制/APK/字节码，用它还原算法；若算法就在前端 JS 里，此辅退场，由 ctf-web 自己读 JS。
3. 拿到 flag 后调用 `/ctf-writeup`（辅）：按 submission 模板产出一份带完整 solve 脚本的 `writeup.md`。

## 每步在干什么

1. **ctf-web 先做首次侦察**：抓一对正常的登录请求/响应，把 cookie 原样解码（base64/hex/点分三段？是 JSON、JWT 形状还是纯二进制块？），再枚举 `/admin`、JS bundle 里的隐藏路由——先弄清服务端「验什么」，再谈「伪造什么」。交付物：admin 身份 + flag。
2. **ctf-reverse 只负责算法还原**：对附件二进制做 strings、常量指纹扫描（crypto-constants.md 的 TEA/AES/RC4 特征表）、必要时 Frida hook 比较函数，产出一段「输入→密文」的精确算法描述和伪造配方，交回 ctf-web 落地。它有明确边界：只是网页里的小段 JS 时不接手（退回 ctf-web）。
3. **ctf-writeup 只在解出后启动**：从会话里收集元数据、exp 脚本、时间线，写一份 1-3 步、单脚本跑通「挑战数据 → 打印 flag」的可复现题解，供队内提交。

## 没结果怎么办

- 解码发现 token 实际是 JWT（点分三段 base64）：切 **`/strix-authentication-jwt`**（令牌伪造、算法混淆与声明篡改），触发动作就是把现成 cookie 喂给它做 alg/none/key-confusion 测试。
- 算法核心是标准密码学原语（AES/RC4 + 密钥泄露）而非纯实现还原：切 **`/ctf-crypto`** 补数学侧攻击。
- 已还原算法但需要先枚举隐藏 admin 端点、进入工具推进阶段：增强到 **`/strix-httpx`**（探测）、**`/strix-katana`**（爬取）、**`/strix-ffuf`**（字典枚举）——开始打具体测试动作时再切，不要一上来全丢给 Strix。
- 手头没有二进制、算法又不在前端：回 ctf-web 检查 source map、`/.git/`、报错页等信息泄露渠道再定位算法。

## 术语一句话

- **自定义加密 token**：出题人自己实现的加签/加密会话凭据，不是标准 JWT，通常要先逆向实现才能伪造。
- **证据补充**：辅助 skill 在主结论形成前提供一块关键拼图（这里是算法描述），不接管主流程。
- **验收约束**：辅助 skill 在主结果形成后校验交付质量（这里是 writeup 可复现性）。
- **算法混淆**：JWT 攻击手法，利用 `alg` 头欺骗服务端用错误算法验签从而伪造令牌。

## 置信度

- **主 skill**：`/ctf-web`
- **备选**：`/ctf-crypto`、`/strix-authentication-jwt`
